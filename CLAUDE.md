# CLAUDE.md

Agent-facing rules for this repository. Detail and procedure live in `CONTRIBUTING.md`; this file states rules only.

## Code in the documentation

A Go block in `README.md` or `docs/` MUST come from a file the compiler and `go test` see. NEVER write a snippet straight into a page, and NEVER hand-edit the body of an include block — write the example under `examples/`, mark it, and run `go test ./examples/ -update-docs`. `TestDocGoBlocksComeFromExamples` fails on a hand-written Go fence, and `TestDocRegionsAreIncluded` fails on a marked region no page includes.

Include a whole file with `<!-- INCLUDE(examples/x_example_test.go) -->`, or one region of it with `<!-- INCLUDE(examples/x_example_test.go#name) -->` against `// BEGIN(name)` / `// END(name)` in the source. CONTRIBUTING.md's "Code in the documentation" section owns the full workflow.

ALWAYS leave a blank line after a marker written at the left margin, so Go does not read it as the following declaration's doc comment and print it from `go doc` and pkg.go.dev. `TestDocRegionMarkersStayOutOfDocComments` fails on a marker that still attaches. A marker indented inside a function body needs no blank line.

An example reads its tables from the generated `examples/store` package, never from a hand-written table declared beside it. A reader copies what the examples do, and almost every reader generates a store, so an example that hand-writes a wrapper shows a shape it claims rasqlgen emits while nothing checks that claim. `TestGeneratedStoreIsCurrent` does check it: add the table to `exampleStore` in `examples/generated_store_test.go`, run `go test ./examples/ -update-docs`, and use `store.Users()` in the example.

A lesson needing a column `users` lacks adds that column to `users`, and NEVER a second table beside it. `members`, `default_users`, and `people` each existed only to carry one column, and a reader met four names for one concept with nothing saying how they differed. The cost of one wide table is that whole-row `SELECT`s in the examples list six columns; that is the accepted trade. A separate table is right only when the lesson is about more than one table, as `orders` is for joins and `employees` is for a self-join.

A hand-written table stays only where the description itself is the lesson, which today is `examples/schema_decimal_column_example_test.go`, `examples/schema_qualified_table_example_test.go`, `examples/schema_table_definition_example_test.go`, `examples/schema_unsigned_column_example_test.go`, and `examples/schema_bind_row_type_example_test.go`. One of those still gets the wrapper type and one accessor method per column, because the next rule applies to it too.

An example names a column through an accessor method, never as a string. `users.ID()` is the call the compiler checks, and a renamed column becomes a build failure; `Table.Column("id")` gives that check up, so an example that reaches for it teaches the weaker form as if it were the normal one.

Three cases keep the string form, and each states why in the example itself. `examples/rasqlgen_column_fields_example_test.go` is the escape-hatch example, and shows what naming a column by string costs. `examples/query_render_select_example_test.go` and `examples/query_render_write_example_test.go` build a `query.TableRef` that carries no Go row type, so no accessor can exist. Anything reading through `rasql/dynamic` names its columns as strings, because that is the builder's only way.

Generated source a page shows is checked in and regenerated by the same flag: every `_gen.go` file under `examples/store`, including `schema_gen.go` and `schema_gen_test.go`. NEVER add a JSON schema snapshot to generate one from — this repository generates from a Go table definition or from migrations applied to a throwaway database, and 29dc9e5 removed the last snapshot.

## Prose in the documentation

State the action before the result it produces. NEVER assume a finished state and then derive the step that produces it ("the server reads an already-built cache, so `rasql widget build` has to run first") — write the step first, then what it leaves behind.

NEVER deny a behavior no reader expects ("the server writes no cache file of its own"). Keep a denial only where a reader would plausibly expect the opposite, such as a scaffolding command that writes one file and opens no database.

## Verifying live database behavior

A claim about what MySQL or PostgreSQL actually does MUST be confirmed against a running server before being reported as verified. `sqlmock` and other fixture tests assert rasql's own output back to itself, never against a real engine, so a passing fixture test proves nothing about real MySQL/PostgreSQL behavior.

Get a live database the single way this repository supports: bring up `compose.yaml` with `docker compose up -d --wait`, then export `RASQL_TEST_POSTGRES_DSN` / `RASQL_TEST_MYSQL_DSN`. `internal/dbtest` starts nothing itself and skips a live test when either variable is unset — this is exactly what CI's `integration` job does. CONTRIBUTING.md's "Live database tests" section owns the full resolution order and containment guarantees; its "Privileges a non-superuser DSN needs" section owns what a non-superuser DSN requires.

`docker compose` MUST be the plugin, never the standalone `docker-compose` binary, at v2.1.1 or later (where `up --wait` arrived).

NEVER report behavior as verified against an engine when only fixture tests ran. Name which engines were actually reachable (e.g. "confirmed against PostgreSQL; MySQL was unreachable").

A new assertion about engine behavior belongs in a live test guarded by `internal/dbtest`, added alongside the existing fixture test rather than replacing it. `text_width_integration_test.go` is the worked example: it pins what a live catalog reports back for a stated text width, and asserts MySQL's own error 1170 rather than trusting rasql's render-time check to describe it.
